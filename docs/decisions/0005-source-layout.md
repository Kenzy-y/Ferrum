# 0005. Раскладка исходников по слоям, крейт shell, обработчики команд

**Дата:** 2026-11-05. **Статус:** принято владельцем.

## Контекст

Все крейты лежали в `crates/` одним списком, поэтому слоёв из AGENTS.md §4.2 по дереву было не видно. Внутри `workbench` и `editor` было примерно по 20 файлов без подпапок. В бинарнике `ferrum` жила логика окна: маршрутизация клавиш, live-reload конфигов, открытие проектов. Команды разбирались ручными `match` в двух местах.

## Решение

- Крейты лежат в `src/`, разложенные по слоям, как в VS Code (`src/vs/{base,platform,editor,workbench}`): `base/`, `platform/`, `languages/`, `design/`, `editor/`, `workbench/`, `app/`. Имена пакетов не менялись. `members` перечислены явно.
- `workbench` внутри разделён на `parts/` (области окна), `contrib/` (фичи, каждая в своей папке) и `dialogs/`. `editor` разделён на `render/`, `input/`, `decorations/` и `highlighting/`.
- Новый крейт `shell` (`src/app/shell`): корневое представление окна, клавиатура, конфигурация, команды приложения, витрина. В `ferrum` остался только `main()`.
- `workbench::CommandHandlers` — таблица «id → обработчик», одна на окно. Её заполняют владельцы команд (`Workbench::register_handlers`, `Shell::register_handlers`) при открытии окна, после этого она только читается. Тест проверяет, что у каждой зарегистрированной команды есть обработчик.

## Последствия

- Новый крейт кладётся в папку своего слоя и вписывается в `members`. Новая фича workbench получает папку в `contrib/`.
- Обработчики живут в UI-слое, потому что им нужны `Window` и `App`. Описания команд остаются в `commands`, который не зависит от GPUI.
- Плагины позже будут регистрировать обработчики через ту же таблицу.
